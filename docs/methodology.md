# Методология расчётов

Проект учебный. Он исследует исторические данные Olist и не описывает коммерческий опыт автора.

## Единица наблюдения и выборка

Одна строка аналитической витрины — товарная позиция, ключ `(order_id, order_item_id)`. Заказ может содержать несколько позиций. `customer_id` относится к записи клиента для заказа; для повторных покупок используется `customer_unique_id`.

В выборку входят заказы со статусом `delivered` и временем покупки от `2017-01-01 00:00:00` включительно до `2018-09-01 00:00:00` исключительно. Граница определяется временем покупки, а не доставки. Даты без распознаваемого значения исключаются. Период фиксирован в коде и SQL; это описание выбранного окна, а не гарантия полноты исходного набора.

В Python полные дубликаты исходных строк удаляются до объединений. При загрузке SQLite скриптом `scripts/load_sqlite.py` применяется то же правило ко всем шести таблицам. Сравниваются все столбцы: разные позиции одного заказа и отдельные части оплаты сохраняются, даже если их суммы совпадают. Загрузчик показывает число удалённых полных дубликатов для каждой таблицы. Исходные CSV не изменяются.

После удаления полных дубликатов загрузчик проверяет ключи:

| Таблица | Ключ записи |
|---|---|
| `customers` | `customer_id` |
| `orders` | `order_id` |
| `order_items` | `order_id`, `order_item_id` |
| `payments` | `order_id`, `payment_sequential` |
| `products` | `product_id` |
| `category_translation` | `product_category_name` |

Каждая часть перечисленных ключей должна быть заполнена. Загрузчик отвергает `NULL`/пропуск, пустую строку и строку только из пробельных символов, включая табуляцию. При нарушении выдаётся `ValueError` с таблицей, составом ключа и количеством ошибочных строк до создания или изменения базы. Значения непустых ключей сохраняются в исходном виде. Правило относится к указанным ключевым полям; отсутствующая категория в таблице товаров по-прежнему допускается и обрабатывается как `unknown`.

Если одному ключу соответствуют разные строки, загрузчик выдаёт `ValueError` с названием таблицы, ключом и количеством конфликтующих строк. Все шесть источников проверяются до открытия SQLite, поэтому конфликт даже в последней таблице сохраняет существующую базу без изменений; при первом запуске файл базы не создаётся. Исправить неоднозначные записи нужно в исходных данных перед повторной загрузкой. Совпадение `customer_unique_id` у разных `customer_id` допустимо: это один покупатель с несколькими заказами.

Товарные строки с отрицательной или отсутствующей ценой либо стоимостью доставки исключаются при расчёте; нулевые значения допустимы. Дорогие позиции сохраняются. Если после отбора у заказа не осталось товарных строк, он не участвует в метриках.

Заказы и товарные позиции объединяются с клиентами по внутреннему соединению. Заказ без соответствующей записи клиента не участвует ни в Python-витрине, ни в одном из девяти SQL-результатов. Если таблица клиентов пуста, аналитическая выборка также пуста. Для SQL-запросов, которым не нужны атрибуты клиента, наличие записи проверяется через `EXISTS`: такая проверка сама по себе не размножает товарные строки. Исходные строки сохраняются в SQLite; правило применяется при расчёте показателей.

Связи с товарами и переводами категорий — левые соединения; отсутствующие категории обозначаются `unknown`, нераспознанные регионы — `Unknown`. В Python проверки кратности соединений и уникальности товарного ключа останавливают расчёт при конфликтующих ключах, способных завысить выручку.

## Определения метрик

| Метрика | Определение |
|---|---|
| Товарная выручка, BRL | Сумма `price` сохранённых товарных позиций; доставка исключена |
| Заказы | Число уникальных `order_id` в витрине |
| Товарные позиции | Количество строк витрины; один номер позиции может встречаться в разных заказах |
| Средний чек, BRL | Товарная выручка / число заказов |
| Уникальные покупатели | Число уникальных `customer_unique_id` |
| Повторные покупатели | Покупатели с более чем одним уникальным заказом в выбранном окне |
| Доля повторных покупателей, % | Повторные покупатели / уникальные покупатели × 100 |

## Когортное удержание повторных покупок

Когорта определяется месяцем первой наблюдаемой доставки для `customer_unique_id` внутри окна анализа. Для каждой когорты считается доля клиентов хотя бы с одним доставленным заказом в каждом из следующих шести календарных месяцев, включая месяц первого заказа. В знаменателе — все клиенты когорты; повторные заказы в одном месяце не увеличивают числитель.

Для сравнения используется только полный шестимесячный период наблюдения: при конце окна 31 августа 2018 года последний допустимый месяц первой покупки — март 2018 года. Клиенты с первой наблюдаемой покупкой после марта не включаются в когортную таблицу, поскольку у них нет всех шести месяцев наблюдения в выбранном окне. «Первая наблюдаемая» не означает первую покупку за всю жизнь клиента: покупки до 2017 года и после августа 2018 года этим анализом не видны. Поэтому это описательная когортная метрика внутри заданного периода, а не причинный эффект.

Средний чек считается по заказам: средняя цена отдельной товарной строки не является средним чеком. Денежные итоги округляются до двух знаков после агрегации.

Один заказ может содержать товары нескольких категорий. Поэтому количество заказов по категориям нельзя суммировать для получения общего количества заказов. Выручка по категориям, регионам и месяцам аддитивна. Таблица `top_products` ограничена двадцатью товарами; её выручка не обязана равняться общей.

Таблица оплат может содержать несколько записей на заказ. Она не присоединяется к товарным строкам при расчёте товарной выручки: такое соединение без предварительного агрегирования может размножить строки.

## Пустая выборка

При отсутствии сохранённых позиций выручка и счётчики равны нулю. Средний чек и доля повторных покупателей не имеют знаменателя и возвращают `None` в Python и `NULL` в SQL. Нулевая выручка при наличии заказов — отдельный допустимый случай: средний чек тогда равен нулю.

## Что подтверждают тесты

Тесты работают с небольшими синтетическими таблицами: заранее известны суммы, количество заказов и покупателей. Они проверяют границы периода, пропуски, отрицательные и нулевые суммы, полные дубликаты, конфликтующие ключи, категории, регионы, повторные покупки и неизменность входных таблиц.

Для всех девяти SQL-запросов проверяются выполнение и ожидаемые результаты; сопоставимые метрики сверяются с Python. Отдельные сценарии проверяют неопределённый рост в первом месяце, равные результаты категорий при ранжировании, когортное удержание и пустую выборку. CI не загружает полный набор данных и не выполняет ноутбук.

Интеграционные тесты отдельно создают исходные CSV с полными дубликатами, загружают их штатным загрузчиком и сравнивают восемь сводных SQL-результатов с чистым контрольным набором. Они также проверяют сохранение разных товарных позиций и частей оплаты с одинаковыми суммами.

Дополнительные интеграционные сценарии удаляют запись клиента и полностью очищают таблицу клиентов. Восемь сводных SQL-запросов сравниваются с контрольным набором, из которого соответствующие заказы исключены; общие метрики и повторные покупки также сверяются с Python.

Сценарии с конфликтующими ключами проверяют отказ загрузки для каждой из шести таблиц и отсутствие нового файла базы. Отдельный сценарий меняет раннюю таблицу и добавляет конфликт в последнюю: существующая база должна остаться побайтно прежней, а выручка и число заказов в ней — сохранить контрольные значения.

Сценарии с незаполненными ключами проверяют все восемь ключевых полей шести таблиц: пропуск, пустую строку и строку с пробелами и табуляцией — всего 24 варианта. Отдельно проверяется побайтная сохранность существующей базы, если незаполненный ключ найден в последнем источнике после изменения ранней таблицы.

Синтетическая сверка Python/SQL не доказывает одинаковое поведение на любых повреждённых данных. Удаление полных дубликатов, проверка заполненности ключей и конфликтов для SQLite обеспечиваются загрузчиком: при самостоятельном заполнении базы эти правила требуется применить отдельно. Ошибочные ключи обнаруживаются, но автоматически не исправляются. Эти проверки не заменяют отдельное правило для прямой обработки повреждённых таблиц функциями Python и проверку целостности остальных связей. Для изменённого набора требуется повторить сверку на всём наборе.

## Границы интерпретации

- Выручка не является прибылью: себестоимость отсутствует.
- Доля повторных покупателей внутри фиксированного окна не является когортным удержанием. Покупатели в конце окна наблюдаются меньше времени; покупки до начала и после конца окна не учитываются.
- Рост месяц к месяцу сравнивает доступные месяцы в SQL. Для набора с пропущенными месяцами потребуется календарная сетка; текущие тесты не утверждают, что пропущенные месяцы заполняются автоматически.
- Рейтинг категорий региона сохраняет все категории с одинаковой максимальной выручкой благодаря `DENSE_RANK`.
- Наблюдаемые связи не устанавливают причин изменений. Рекомендации требуют последующей проверки.
